# Retrieval from first principles

## The idea

A small model knows only what it learned in training. Retrieval-augmented generation (RAG) gets around that at question time. Find the passages relevant to the question, paste them into the prompt, and let the model answer from them. The hard step is the retrieval itself. This lesson uses TF-IDF, a word-counting method, as a stand-in for the learned embeddings used in real systems.

Worked example of cosine similarity. Take two vectors over the words [cat, dog, fish]: a = [1, 2, 0] and b = [2, 1, 0]. Their dot product is 1 x 2 + 2 x 1 + 0 x 0 = 4. Each has length sqrt(1 + 4) = 2.236. The cosine similarity is 4 / (2.236 x 2.236) = 4 / 5 = 0.8. Cosine similarity ignores length and compares direction. A value of 1 means the same direction, and 0 means no shared direction.

Worked example of TF-IDF. Suppose there are 4 notes and the word `embedding` appears in 2 of them. Its inverse document frequency is ln(N / df) = ln(4 / 2) = ln 2 = 0.693. A word that appears in all 4 notes gets ln(4 / 4) = 0, so it carries no weight at all. Being common, it says nothing about which note is relevant. The lab uses a smoothed form, idf = ln((1 + N) / (1 + df)) + 1, which keeps every weight positive.

## How it works

1. Split the notes file into notes, one per line.
2. Build a vocabulary of words. For each note, make a vector whose entries are the word counts times the IDF weights.
3. Turn the question into a vector over the same vocabulary, using the same weights.
4. Compute the cosine similarity between the question vector and each note vector.
5. Sort by score, keep the top `TOP_K` notes, and assemble the prompt: the retrieved notes as context, then the question.

The similarity function is short:

```python
def cosine(a, b):
    denom = np.linalg.norm(a) * np.linalg.norm(b)
    return float(a @ b / denom) if denom else 0.0
```

TF-IDF matches shared words only. The words `car` and `automobile` do not match, even though they mean the same thing. Learned embeddings map similar meanings to nearby vectors, and that is why they retrieve better. Long documents also need chunking, which cuts them into pieces small enough to fit in the context window. A chunk boundary can split an answer in two, so chunk size and overlap matter.
